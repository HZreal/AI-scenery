# 第二阶段：Prompt 与上下文工程实践讲解

本阶段研究的不是“写一句更像人话的提示词”，而是如何把模型行为约束、参考资料与用户任务组织成可维护、可对比的后端输入。

对应 Demo 是 [02-prompt-context](../demos/02-prompt-context/README.md)，核心接口为 `POST /api/prompt-context`。

## 1. Prompt 是后端契约的一部分

模型输出会受指令、示例、上下文、模型版本和采样配置共同影响。若 Prompt 直接散落在 Handler 中，无法回答“本次请求到底使用了哪份规则”“改动后好在哪里”“出问题能否回滚”。

因此 Demo 将 Prompt 定义为带版本号的 `Version`：

- `baseline-v1`：只保留角色和直接任务，作为基线。
- `grounded-v2`：增加固定规则、上下文边界与一个示例，用于验证更强约束是否更稳定。

版本号不是装饰。它是评测样例、日志、灰度发布和回滚的共同索引。

## 2. system、developer、user 的职责

从应用设计角度可这样区分：

| 层次 | 谁控制 | 内容 |
| --- | --- | --- |
| system | 系统/平台 | 身份、不可突破的安全边界、全局行为 |
| developer | 应用开发者 | 当前产品规则、输出格式、领域约束 |
| user | 最终用户 | 具体问题、目标、可变资料 |

Gemini `GenerateContent` 的消息表达是 `SystemInstruction`、`user`、`model`，没有独立的 developer role。Demo 因而将开发者规则写进由服务端构造的 system instruction 的 `<rules>` 区段；用户不能通过 HTTP 参数替换它。

## 3. 上下文不是越多越好

模型的 context window 是输入与输出合计上限，但应用仍要有更小的业务预算：过长输入会增加延迟和成本，也会把无关内容带入推理。

Demo 的 `PROMPT_CONTEXT_MAX_CHARS` 是字符级学习用预算，不等同 token 预算。超限时它保留上下文的前 60% 与后 40%，并插入裁剪标记；这是一个可解释的起点，不是通用最优策略。

长资料的排列顺序同样重要。`grounded-v2` 先放 `<context>`，后放 `<task>`，并以“基于以上参考资料”锚定任务。这符合 Gemini 官方长上下文指南对“将问题放在资料之后”的建议。

## 4. few-shot 与结构化边界

Few-shot 不是堆砌大量范例，而是用少量、具体、具有代表性的输入输出展示目标模式。Demo 的示例说明：资料中有 SSE `delta` 事件时，页面为何能增量显示文本。

XML 风格的 `<context>` 与 `<task>` 是边界标记，不是安全沙箱。它们降低“资料与指令混在一起”的歧义；后续安全阶段还会专门学习 prompt injection 与不可信资料处理。

## 5. 如何比较 Prompt 版本

对比 API 一次对同一个 `task` 运行多个版本，并回传：

- version、system instruction 与最终 user prompt；
- output；
- 每个版本的延迟和输入/输出 token；
- 上下文原始长度、使用长度与裁剪状态。

比较时不要只问“哪段话更顺”。先写评估维度，例如是否回答了任务、是否只基于资料、格式是否稳定、是否过度冗长、延迟与 token 是否可接受。对于同一输入，最好重复多次；模型输出本身有波动。

## 6. 上游暂时不可用的边界

Prompt 的对比调用依赖真实模型服务。Demo 仅对 `503`（服务暂时繁忙）配置最多三次尝试的退避重试；`429` 配额耗尽会直接返回 `provider_quota_exceeded`，避免无意义等待。鉴权、参数错误和其他业务错误会直接返回，并保留 `trace_id`，让调用方可以区分上游故障和自己的输入校验错误。

## 7. 本阶段边界与下一步

当前 Demo 使用真实 Gemini 做单轮对比，未持久化 Prompt 版本、未保存评测集、未使用 token 精确计数，也没有自动选择胜出版本。它的目的是建立“Prompt 可以像代码一样版本化与验证”的习惯。

下一步可继续完成：

1. 增加更多版本，例如无 few-shot、带 few-shot、结构化输出版本。
2. 为固定输入建立人工评分表或简单断言，形成最小 eval set。
3. 将长会话历史做摘要或选择性保留，为后续记忆与 RAG 打基础。
